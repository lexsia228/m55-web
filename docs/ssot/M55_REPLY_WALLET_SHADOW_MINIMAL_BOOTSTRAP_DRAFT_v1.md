## 2. 対象に含める migration 候補と判定（含める／保留／不要）

※ **判定はすべて「この最小 draft の目的」（Phase A PART 1 が読める）に縮んだもの。** **`supabase/migrations` ファイルを唯一の正とし、`CREATE`〜等のコード本文は本条に転記しない。** ※ **`202604220...` と `210...` はファイル名を正式版で参照：** `20260421000000_dtr_postgrest_schema_reload.sql`、`20260422000000_dtr_guest_drafts_report_snapshots_columns_pgrst204.sql`。

### 2A. **`20260416000000_reply_system_data_layer_v1.sql`**

| 項目 | 判定 |
|------|------|
| **含めるか** | **含める。** |
| **理由** | `reply_ticket_wallets` / `reply_wallet_ledgers` / `reply_sessions` の **単一ソース**となる migration。** PART 1 preflight が参照する三表および付随インデックス・制約の正規定義。** 同一ファイルが **`reply_documents` および相互 FK を合わせて定義している** — Phase A が **読みを要求するだけのときも**、ファイルを分割しない（**手書き DDL 禁止および Reject SSOT**）。 |
| **前提** | **`gen_random_uuid()` などの DB 関数が利用できること。** 拡張行はファイル外の別途前提とする（dependency map と同旨）。 |
| **備考（列挙しない）** | ファイル先頭〜末尾は **DDL とコメント（migration 本文上、シード無し）**。 |

### 2B. **`20260420000000_dtr_drafts_and_report_snapshots.sql`**

| 項目 | 判定 |
|------|------|
| **含めるか** | **含める。** |
| **理由** | **`dtr_report_snapshots` が PART 1 の orphan カウントに必須。** 同一 migration が **`dtr_guest_drafts` とペア作成**になるため、**ユーザーが列挙した「最小4テーブル」だけへ切り出すことをせず、`dtr_guest_drafts` は副産物として受け入れる** — それがないと **`202604220....` と整合しない列追加が適用できない**（論理依存）。 |
| **前提** | **特になし。**（dependency map の独立オブジェクトグループ）。 |
| **備考（列挙しない）** | DTR 両表および index／comment が同一ファイルにある。 |

### 2C. **`20260422000000_dtr_guest_drafts_report_snapshots_columns_pgrst204.sql`**

| 項目 | 判定 |
|------|------|
| **含めるか** | **基本は含める（本番側と列集合を揃える目的）。** |
| **理由** | **`dtr_report_snapshots` における運用・アプリ側が参照する列の一部が、より古い状態からの後追き追加だった場合の是正**を意図した migration（ファイル先頭コメント参照）。 **本番適用済みと一致させる場合、列セットの観点で有益。** 「手貼り `ALTER`」としてではなく **`202604220` ファイル由来の順序付き適用**としてのみ扱う。 |
| **前提** | **`202604200....` が先に済んでいること。** 対象両テーブルが存在しないと失敗の論理になる。 |

**論点：** 同一ファイル末尾に **`NOTIFY pgrst`** のみの副作用がある。**本番 DDL の「論理モデル」を壊すものではないが、環境側の PostgREST／プールコンテキストの有無で意味が変わる。** → **§2D とセットで評価。**

### 2D. **`20260421000000_dtr_postgrest_schema_reload.sql`**

| 項目 | 判定 |
|------|------|
| **保留／検討** | **`202604210` は DDL を伴わず通知のみ。** `202604220....` の末尾にも **同種の通知のみ** が含まれ得る。**重複適用でも通常は害が少ないが、適用順序と「単独で読むときの論理」だけ整理する。** |
| **結論ドラフト** | **最小 DDL 状態の達成だけが目的なら `202604210` 単独は任意。** **`202604220....` が既に類似通知を含む場合、二重 NOTIFY を避ける運用でもよい。** **本番準拠性（列）は `210` が与えず、`220` 側が DDL + 通知となる。** **`210` は「API レイヤーのキャッシュ不整合が疑われるときの追加」または「読み順の忠実再生」ときにのみ含める。** |
| **`含める`** | **環境運用規約として「適用済みリストに必ず並べたいとき」**。 |
| **`不要`** | **`220` が通知まで含んだうえ、`210` と重なると読み順まで厳密に再現しない場合でも可。** |

---

### 小括（順序のみ言語化）

論理順は **`202604160` → `202604200` → `202604220`**。** `210` が入る場合は **`200` と `220` のあいだのいずれか**（単独 NOTIFY であれば前後とも可 — 環境運用のみ）。 **`220` と `210` で NOTIFY が二重にならないかだけ合意すべき。** **本番 DDL 列一致を最優先とする。**

## 4. 「正規 DDL 抽出」の方針（いま実行可能 SQL は作らない）

| # | 方針 |
|---|------|
| 1 | **手書き `CREATE TABLE`／手貼り簡易スキーマは禁止**（Rejected SSOT）。 |
| 2 | **`supabase/migrations` を唯一の正とし、適用単位は原則「ファイル単位」** が安全。単一ファイル内に **複数オブジェクトがある場合はすべて一括適用が原則** — **部分抽出は「そのファイルのみをソースとする verbatim スニペット」でない限りしない。** |
| 3 | **migration 内にデータ挿入またはシードがある場合：** **当該ファイルを分割適用しない**か、または **将来、別ファイルにより DML と DDL をフェーズ分割するのは別承認** — **現時点では `202604170` は本条の最小セットに入れず、種データ問題を発生させない。** |
| 4 | **DDL「だけ」を後日抽出するとき：** **抽出理由**（例：`dtr_guest_drafts` を副産物としたくない論点への対処 — ただし **手書きに落ちるなら停止条件 §6**）および **ソース migration の行番号範囲**（レビュ時点のリポ）をワークログに書く。** 本条自体では **コードブロックとして SQL は書かない。** |
| 5 | **`202604220` の DDL 部分：`202604200` 適用済みがあることが前提になる列追加** — 「抽出」論点だけなら、その前提を列挙し、実行はしない。 |

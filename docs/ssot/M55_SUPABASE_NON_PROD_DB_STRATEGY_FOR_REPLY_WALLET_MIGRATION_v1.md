## 2. 選択肢比較（A〜E）

凡例：**◎**向く／**△**条件付き／**×**不採用寄り。**コスト・難易度は目安**（プラン・組織により変動）。

### A. Supabase Branching / Preview Branch

| 観点 | 評価 |
|------|------|
| **安全性** | **本番 DB を「直接 DDL しない」検証経路になりやすい。** ブランチが論理的に分離されている前提。誤環境混入は運用チェックリストで抑止。 |
| **本番データ再現性** | ブランチの仕様により **フォーク時点で近い状態**を寄せられる場合がある。**常に本番と完全一致とは限らない。** |
| **PII / 個人情報** | ブランチに複製データが載る。**「非本番の個人情報」の取り扱いと保存期間**をポリシー化する必要あり。 |
| **コスト** | **プラン依存**（Branching が含まれるか）。削除・寿命で変動。 |
| **セットアップ難度** | **低〜中**（Dashboard から作成できる場合。**プロジェクト側で機能有効化が前提**）。 |
| **nullable DDL の検証** | **◎** `ALTER ... ADD COLUMN` の成否・ロックの感触を試せる（データ量にも依存）。 |
| **PART 1 件数検証** | **△〜◎** **スキーマは本番に近い**が、ブランチのデータ規模・複製タイミングで件数が本番と一致しないことがある。**「本番との同値」証明は別クエリ**。 |
| **採用判定** | **採用候補（第一候補）** — 本番を直接編集せず、**同一ブランドでの事前検証**に向くため。機能が無い・権限が無いときは別案へ。 |

### B. 新規 shadow / staging project

| 観点 | 評価 |
|------|------|
| **安全性** | **◎** **本番 project ref と必ず異なる**。誤認しにくいなら安全。 |
| **本番データ再現性** | **△** **空に近い**か、**移行/migration のみ**でスタートするのが通常。**本番件数再現はバックアップ投入が別途必要**。 |
| **PII** | 本番からコピーする場合は **E と同程度の PII 管理**が要る。空なら低い。 |
| **コスト** | **追加プロジェクト分**（無料枠の使い方次第）。 |
| **セットアップ難度** | **中**（プロジェクト作成、`supabase/migrations` または手順でスキーマ整合、必要なら seed）。 |
| **nullable DDL** | **◎** |
| **PART 1 件数** | **△** 本番オーバーレイが無い限り **件数は「検証用」**に留まる。 |
| **採用判定** | **採用候補（第二候補）** — Branching が使えない／ポリシーで「常に独立プロジェクト」のとき。 |

### C. 本番バックアップを非本番へ restore

| 観点 | 評価 |
|------|------|
| **安全性** | **△** **本番を触らないが、コピー先は本番相当の敏感データの塊**。**誤接続・誤共有のリスク最大クラスに近い。** |
| **本番データ再現性** | **◎** **件数・分布は最も近い**（復元時点依存）。 |
| **PII** | **高** — **職場のデータ保護・保管場所・アクセス制御・保存期間**を文書化必須。 |
| **コスト** | ストレージ・インスタンス・運用。 |
| **セットアップ難度** | **高**（restore 手順、ロール、RLS、拡張の一致）。 |
| **nullable DDL** | **◎** |
| **PART 1 件数** | **◎**（本番観測に近い） |
| **採用判定** | **限定採用** — **PII 手続きと隔離が明文化される場合のみ**。デフォルトの第一候補にはしない。 |

### D. Local Supabase（CLI 等）

| 観点 | 評価 |
|------|------|
| **安全性** | **◎（ローカル）** — クラウド本番とは無関係。**他人と共有しない限り**。 |
| **本番データ再現性** | **×〜△** — **DDL 試験向き**。本番データ件数は別途入力しない限り無い。 |
| **PII** | **低**（本番複製しない限り）。 |
| **コスト** | **低**（主に開発者時間）。 |
| **セットアップ難度** | **低〜中**（Docker／CLI に慣れが要ることがある）。 |
| **nullable DDL** | **◎** **構文・マイグレーション順序のチェック**。 |
| **PART 1 件数** | **△** — **本番件数とは無関係**。**件数検証は「ローカル専用」または保留**。 |
| **採用判定** | **補佐として採用** — 「**DDL だけ先に確認**」「Branch / shadow が未整備」の間のつなぎ。 |

### E. 本番で SELECT のみ実行

| 観点 | 評価 |
|------|------|
| **安全性** | **△** — **読み取りでも** 本番接続ログ・運用規程・コンプライアンス上 **`SELECT` が許されるか個別判定**。**PART 3 に相当するクエリは列未追加で失敗することも。** |
| **本番データ再現性** | **◎（そのまま本番）。** |
| **PII** | **クエリ結果に含まれる** — 転記ミスやチケット漏洩対策が要る。**hash-only 診断 SQL の運用との整合**。 |
| **コスト** | **低**。 |
| **セットアップ難度** | **最小**。 |
| **nullable DDL** | **×（Phase A DDL は検証にならない）**。 |
| **PART 1 件数** | **実務上はできるが、「Phase A を進めた」の証明にはならない**。 |
| **採用判定** | **本稿では Phase A 検証ルートとして不採用。** **監査上の読み取り**は別チャネルの SSOT と整合で扱う。 |

## 3. 推奨案

| 順位 | 案 | 理由 |
|------|-----|------|
| **第一候補** | **A（Supabase Branching / Preview Branch）** — **利用可能なら** | 本番 project を **DDL で直接変更せず**、**同一サービス境界内で DDL の感触とスキーマ近傍を試せる**。非本番 ref を **Dashboard で環境として区別しやすい**ことが多い。 |
| **代替候補** | **B（新規 shadow/staging project）** | Branching が **プラン・組織方針で不可**なとき。**project ref が本番と明確に別**になり、恒久の「検証専用」にできる。 |

**原則不採用:** **main / PRODUCTION に対して Phase A の PART 1〜4 を実行する**こと（**読み取りのみといえど、本検証経路としては許可しない**。業務監査での read-only が別にある場合は **別 SSOT**）。

**PART 2（ALTER）は** **非本番でも** **`M55_REPLY_WALLET_PHASE_A_NULLABLE_ONLY_EXECUTION_PACKET_v1`** の承認があるまで実行しない。

## 4. 非本番環境の最低条件

すべて満たすこと。

| # | 条件 |
|---|------|
| 1 | **`project ref` が本番と異なる。** |
| 2 | **Dashboard 上で** staging / dev / preview / branch 等、**運用チームが合意したラベル**で **本番と誤認しない**。 |
| 3 | **バックアップ／復元／破棄**の方針が **チーム文書または Runbook で一言でもよいので存在**する。 |
| 4 | **service role・DB URL・秘密鍵**を **チャット・公開チケット・ログ**に貼らない。 |
| 5 | **実行チケットに `project ref` を記録する場合** — **公開リポジトリにコミットしない**。**アクセス権のあるチケットのみ**。必要なら **ref の一部マスク運用**は組織方針に従う。 |
| 6 | **本番データを複製する**経路（C やブランチのデータコピー含む）は **PII の保管場所・保持期間・アクセス権・削除まで** を **事前に文言化**する。 |

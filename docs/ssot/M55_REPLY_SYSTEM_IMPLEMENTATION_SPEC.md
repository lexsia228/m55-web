1\. 目的

無料の core でユーザーに「自分の輪郭」を渡し、その先で「本質の読み解き」と「相談返書」に接続する。AI は吹き出し会話ではなく、見えている傾向を前提に整理された返書を返す。商品全体の役割は、輪郭 → 構造 → 悩み接続、の順で深まることです。



2\. スコープ

今回の第1スコープは、価格詳細の最終実装ではなく、システムの骨格です。

やることは、無料境界、有料境界、返書1本の生成、返書 JSON、返書 UI、entitlement 真実の置き場所、保存再閲覧の器までです。

やらないことは、価格表現の最終チューニング、追加券の細かい販売導線、複数商品群の棚分けです。そこは後段でよいです。



3\. 無料 / 有料境界

無料で見せるのは、ヒーロー、傾向の輪郭、M55 の読み方、傾向と負荷、このタイプはどう出やすいか、まで。

まず整えるとよいこと から下をフェンス領域とし、この輪郭から見えていること、相談返書導線、本質の読み解き CTA を有料接続領域に置きます。これは、無料は輪郭、有料は読み解きと返書、という商品構造に一致します。



4\. ドメインモデル

最低限必要なデータ構造は6つです。



CoreProfile

core 結果の静的要約。5軸、type、輪郭文、負荷文、生活文を持つ。



PaidReading

本質の読み解き 本体。保存版の本文、生成日時、対象ユーザー、version を持つ。



ReplyTheme

返書テーマ。仕事、人間関係、疲れやすさ、判断の迷い、整え方、距離感、など。



ReplyTicketWallet

返書残数の真実。初回無料分、追加分、消費済み本数、有効状態を持つ。これは DB 側が SSOT。



ReplyRequest

ユーザーが返書を生成するときの入力。theme、subquestions、freeText、coreProfileRef、walletRef を持つ。



ReplyDocument

AI が返す構造化返書。UI はこれをカード群に描画する。



5\. 状態遷移

状態は最低でも次の7つに分けます。

無料閲覧中。

本質の読み解き 購入済み。

初回返書未使用。

返書残数あり。

返書生成中。

返書閲覧済み。

追加返書待ち。

この状態遷移を先に決めておくことで、UI 先行で権利が壊れる事故を防ぎます。entitlement の真実は必ずサーバー側に置き、UI は表示だけにするべきです。



6\. 返書 JSON 仕様

AI に自由文を返させず、まずこの JSON を返させます。

最低フィールドは、theme, issue\_summary, current\_flow, background\_tendency, load\_point, first\_step, next\_question。

実運用ではさらに、supporting\_axes, caution\_note, tone\_label, followup\_prompts, version を追加してよいです。

UI はこの JSON を 4〜6 枚のカードに展開します。これで「ただのチャット」ではなく、M55 の返書として多層提示できます。



7\. 返書生成パイプライン

最初の実装は 1 本だけです。

入力は、core 結果、選択テーマ、選択補助質問、自由入力。

出力は固定した返書 JSON。

ここではまだ複数本管理や販売の詳細には広げません。まず「1本、安定して、同じ構造で返る」を達成するのが先です。



8\. AI の役割定義

AI はユーザーの入力を雑談的に広げる役ではありません。既に見えている傾向を前提に、今の論点を整理し直す役です。

したがって、出力の基本構成は、今の論点、今起きている流れ、背景にある傾向、負荷が集まる場所、先に整えること、今回の一歩、次に深掘りできる問い、の順が適切です。これは V3 正本の「動き方、疲れ方、考え方、整え方を見つめ直す」という方針と一致します。



9\. UI 仕様

返書 UI は v0 で先に組むのが最適です。

左に入力領域、右に返書カード領域。

左には、テーマ選択、補助質問、自由入力。

右には、今の読み、背景の傾向、負荷の集まり方、整え方の入口、次に聞くと深まること、のカード群。

吹き出しチャットは禁止ではないですが、主 UI にはしない方がよいです。v0 に任せるのは、返書カード UI、テーマ選択 UI、補助質問 UI、残数表示 UI、フェンス見た目です。ロジックは入れません。



10\. API 仕様

最小セットは4本です。



GET /api/core/{userId}

core 結果を返す。



GET /api/reply/wallet

返書残数と初回無料分の状態を返す。



POST /api/reply/generate

入力を受け、返書 JSON を生成し、必要なら残数を減算する。



GET /api/reply/history

保存済み返書を返す。



ここで重要なのは、/generate の中で必ず wallet を確認し、消費可否判定と減算をサーバー側で行うことです。UI で減らしてはいけません。



11\. フェンス仕様

core ページでは、まず整えるとよいこと から下を有料フェンスにします。

見出しと導入は見せ、本体は半見せ。

この輪郭から見えていること は 1 項目だけ見せ、残りはマスク。

相談返書セクションは概念だけ見せて、返書実物はサンプルまたは半見せ。

最後に 本質の読み解き CTA を明確に置く。

この構造なら、無料で「自分ごと化」は起きるが、整え方と深掘りはまだ渡し切らない状態を作れます。



12\. 保存と再閲覧

返書は単発表示で終わらせず、保存して読み返せることが必須です。

テーマ別履歴、生成日時、残数、次に使えるテーマをマイページで見えるようにします。

これがないと、M55 の価値が「その場のチャット」で終わってしまいます。保存版として持ち帰れることが商品価値です。



13\. 実装順序の固定

ここからの実作業順はこれで固定します。



まず、docs/ssot/M55\_REPLY\_SYSTEM\_IMPLEMENTATION\_SPEC.md を SSOT として確定させる。



次に、状態遷移図と entitlement 仕様を切る。



その次に、返書 JSON schema を切る。



それから、/api/reply/generate の stub を作る。

この段階では、返書 JSON を安定して返すことを優先し、entitlement の実消費はまだ接続しない。



次に v0 で返書ルーム UI を作る。

v0 は見た目専用とし、ロジックは入れない。



その後に core フェンスを実装する。



最後に entitlement 消費、購入接続、保存再閲覧へ進む。

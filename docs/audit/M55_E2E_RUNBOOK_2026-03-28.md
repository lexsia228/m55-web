## STEP 1 — Gate fail-closed（A系）

**Account-A: unauthenticated（ログアウト状態）**

```
1-1. シークレットブラウザで /dtr/core を開く
     → /dtr/lp へ redirect (302) することを確認（A-1）
1-2. room の実 URL（/dtr/core?room=1 等 or room route）を直接開く
     → アクセス不可（redirect or 403）を確認（A-5）
```

**Account-B: authenticated / no entitlement**

```
1-3. Clerk でサインイン（entitlement なし）
1-4. /dtr/core を開く
     → /dtr/lp へ redirect（locked state）を確認（A-2）
1-5. room route を直接開く
     → アクセス不可（redirect）を確認（A-6）
```

**Account-C: expired entitlement**

```
1-6. Supabase Studio で該当ユーザーの entitlement_rights 行の
     expires_at を過去日（例: 2020-01-01）に手動設定する
     確認カラム: user_id / right_key（例: m55_p:core_origin）/ expires_at
1-7. /dtr/core を開く
     → /dtr/lp へ redirect（expired state 表示）を確認（A-3）
1-8. /dtr/lp?state=expired を直接開く
     → expired notice と purchase CTA が表示されることを確認（A-4）
1-9. 確認後 expires_at を元の値または将来日に戻す
```

## STEP 2 — Purchase flow（B系）

**Account-B（or fresh account）: authenticated / no entitlement**

```
2-1. /dtr/lp を開く
2-2. Entry Report の CTA をクリック
     → Stripe Checkout ページが開くことを確認
     → SKU 名・金額（¥1,000）・商品名を目視確認（B-1）
2-3. テストカード（4242 4242 4242 4242）で支払いを完了する（B-2）
     → /purchase/success または指定 redirect 先に遷移することを確認
2-4. Stripe CLI のターミナルで checkout.session.completed イベントが
     受信されたことを確認（B-3）
2-5. Supabase Studio で entitlement_rights テーブルを確認（B-3）
     確認カラム:
       user_id       — 購入したユーザーの Clerk ID
       right_key     — 'core_origin' または 'm55_p:core_origin' であること
       expires_at    — null（永続）または将来日であること
       created_at    — 購入時刻に近いこと
2-6. /dtr/core を再度開く
     → locked/expired redirect が出ず、全文が表示されることを確認（B-4）
2-7. /my を開く
     → 購入済みレポートが library に表示されることを確認（B-5）
```

## STEP 3 — Room and credits（C系）

**Account-D: owned（STEP 2 の購入済みアカウント）**

```
3-1. /dtr/core を開き、concierge room の CTA をクリックして room に遷移する
     CTA 経由が正規ルート。直接 URL でのアクセスも同一結果になることを確認（C-1→C-2）
     room URL 例: /dtr/core#room または /room/core（実装に従う）
3-2. room 表示で credits 1/1 が UI に反映されていることを確認（C-2）
     Supabase consult_threads で確認:
       user_id                  — 該当ユーザー
       right_key                — 'core_origin' または 'm55_p:core_origin'
       consult_credits_total    — 1
       consult_credits_remaining — 1
3-3. 正常なメッセージ（10 文字以上・500 文字以内・high-risk なし）を入力して送信（C-3）
     → user message が表示される
     → AI response が返ってくる
     → credits 表示が 0/1 に変わる
3-4. Supabase で確認:
     consult_threads:
       consult_credits_remaining — 0 に変わっていること
     consult_messages:
       role='user' の行 1 件 が insert されていること
       role='assistant' の行 1 件 が insert されていること
       計 2 行のみ（orphan なし）
3-5. room を reload する
     → read-only state になっていることを確認（入力欄が disabled または非表示）（C-4）
     → credits 0/1 が表示されていること
3-6. credits 0 の状態で送信を試みる（C-5）
     → ブロックされることを確認
     → Supabase consult_messages に新しい行が追加されていないことを確認
     → consult_threads の consult_credits_remaining が 0 のまま変動しないことを確認
```

## STEP 4 — Input guard edge cases（D系）

**Account-E: owned / credits fresh（consult_credits_remaining = 1）**
*Supabase で consult_threads の consult_credits_remaining を 1 に UPDATE してリセット*

```
4-1. 9 文字以下のメッセージを送信（D-1）
     → ブロック（送信されない）
     → Supabase consult_credits_remaining 変動なし
4-2. 501 文字以上のメッセージを送信（D-2）
     → ブロック
     → Supabase consult_credits_remaining 変動なし
4-3. high-risk ワード含むメッセージを送信（D-3）
     ※ 具体的ワードは AI_CONSULT_SAFETY_AND_LIMITS_SSOT に従う
     → ブロック
     → Supabase consult_credits_remaining 変動なし
4-4. 正常送信中に連続 2 回クリック（double-submit）（D-4）
     → 2 通目がブロックされる（sendLock または pending guard）
     → consult_messages は user 1 件 + assistant 1 件 のみ
     → consult_credits_remaining は 1 回分（1→0）のみ減算
4-5. （任意・AIタイムアウト再現が可能な場合のみ）AI call 失敗（D-5）
     → consult_messages に orphan user 行が残らないこと
     → consult_credits_remaining 減算なし
     → UI はエラー表示（送信可能状態に戻る）
     ※ 再現が困難な場合は「手動確認不可・コード実装確認のみ」と記録する
```

```
     キャンセルで中断する（F-1）
     → Supabase entitlement_rights に新しい行が insert されていないことを確認
5-2. Stripe Dashboard で同一 event_id の webhook を手動 resend する（F-3）

5-3. F-2（webhook 未到達）は E2E pass/fail 判定対象外
     手動プロビジョニング手順が運用 doc に存在することを確認するのみ
```

## Pass criteria
